= MCP

前のモジュールでは、バックエンドデータベース、REST API、および MCP サーバーをデプロイしました。
このモジュールでは、MCP サーバーを Llama Stack に登録する方法と、AI アプリケーション開発の主要言語である Python を使用して Llama Stack および MCP ツールとプログラムで対話する方法を実証します。

MCP ツールを消費するエージェントを構築するための 2 つの異なるアプローチを探索します。

1. **Llama Stack クライアント (Llama Stack Client)**: Llama Stack 用のネイティブ Python SDK であり、ツール呼び出しへの直接アクセスを提供します。
2. **LangGraph**: 推論バックエンドとして Llama Stack を使用する、人気のサードパーティ製エージェントフレームワークです。

どちらのアプローチも、単純なツール呼び出しから複雑な多段階推論まで、エージェント開発における重要なパターンを示しています。

== エージェント開発への 2 つのアプローチ (Two approaches to agent development)

Llama Stack の柔軟なアーキテクチャは、複数の開発パターンをサポートしています。

**直接的なツール呼び出し (Llama Stack クライアント) (Direct tool invocation (Llama Stack Client))**::
最適：ロジックを自分で制御し、プログラムでツール呼び出しをオーケストレーションする場合
- どのツールをいつ呼び出すかを自分で決定します。
- 確定的なワークフロー、テスト、および統合シナリオに役立ちます。
- ツールの呼び出し、パラメーターの受け渡し、および結果の処理を完全に制御できます。

**エージェント駆動の呼び出し (LangGraph + Llama Stack) (Agent-driven invocation (LangGraph + Llama Stack))**::
最適：ツールの使用について推論する自律型エージェントを構築する場合
- ユーザーの意図に基づいて、エージェントがどのツールを呼び出すかを決定します。
- 対話型インターフェース、カスタマーサポート、および複雑な問題解決に役立ちます。
- エージェントがツールの選択、パラメーターの抽出、および結果の統合を処理します。

このモジュールでは、ユースケースに合わせて適切なアプローチを選択できるように、両方のパターンを実証します。

== アプローチ 1: Llama Stack クライアント (直接的なツール呼び出し) (Approach 1: Llama Stack Client (direct tool invocation))

Llama Stack クライアント SDK は、すべての Llama Stack 機能へのプログラムインターフェースを提供します。このアプローチを使用する場合、Python コードがどのツールをいつ呼び出すかを明示的に決定します。つまり、エージェントに推論させるのではなく、ツール呼び出しを自分でオーケストレーションします。

このアプローチは次のような場合に役立ちます。
- 既知のツールシーケンスを持つ確定的なワークフローがある
- ツールの接続性とレスポンスをテストしている
- ツールの選択がルールベースである統合を構築している
- エラー処理や再試行をきめ細かく制御する必要がある

=== Llama Stack クライアント: Customer (Llama Stack Client: Customer)

Llama Stack クライアントでの Customer 向けのコードで注目すべき主要な要素は、クライアントの作成です。

```python
client = Client(
    base_url=BASE_URL,
    api_key=API_KEY
)
```

そしてツールの呼び出しです。

```python
result = client.tool_runtime.invoke_tool(
    tool_name="search_customers",
    kwargs={"contact_email": email}
)
```

Llama Stack クライアントのアプローチは、ワークフローを自分で制御する直接的なツール呼び出しを実証しています。次の点に注目してください。

- LLM の推論は関与していない。これは純粋なツールの実行です。

このパターンは既知のワークフローには効率的ですが、自然言語の入力に基づいてどのツールを使用するかを推論するエージェントの能力を活用していません。

== アプローチ 2: Llama Stack を使用した LangGraph (エージェント駆動の呼び出し) (Approach 2: LangGraph with Llama Stack (agent-driven invocation))

LangGraph は、グラフベースの実行モデルを使用してステートフルなマルチエージェントアプリケーションを構築するためのフレームワークです。Llama Stack と統合すると、LangGraph は推論のために Llama Stack の Response API（または ChatCompletion API）を使用しつつ、高度なエージェントオーケストレーション機能を追加します。

=== なぜ Llama Stack で LangGraph を使用するのですか？ (Why use LangGraph with Llama Stack?)

**LangGraph がエージェント機能を追加します**::
- **自律的なツールの選択**: エージェントがユーザーの意図に基づいてどのツールを呼び出すかを決定します。
- **自然言語理解**: 対話型の入力からツールのパラメーターを抽出します。
- **多段階推論**: 複数のツール呼び出しを連鎖させて、複雑な質問に答えます。
- **状態管理**: ターンの枠を超えて会話のコンテキストを維持します。

**Llama Stack が推論レイヤーを提供します**::
- **モデルサービング**: vLLM がモデル推論の重労働を処理します。
- **ツールランタイム**: Llama Stack のツール実行を通じて MCP サーバーが呼び出されます。
- **統合 API**: LangGraph は標準の OpenAI 互換エンドポイントを使用します。

**これらが合わさることで、本番環境のエージェントアプリケーションが可能になります**::
- LangGraph がエージェントのワークフロー（何をすべきか）をオーケストレーションします。
- Llama Stack が操作（どのように行うか）を実行します。
- MCP サーバーがビジネスシステム（どこからデータを取得するか）に接続します。

### LangGraph と Llama Stack の統合 (LangGraph integration with Llama Stack)

LangGraph は OpenAI 互換の API を介して Llama Stack に接続するため、異なる推論プロバイダー間での切り替えが容易です。主な統合ポイントは以下の通りです。

**OpenAI 互換エンドポイント (OpenAI-compatible endpoints)**::
Llama Stack は、OpenAI の API 仕様に従った `/v1/chat/completions` および `/v1/responses` エンドポイントを公開しています。LangGraph は、OpenAI の GPT モデルと話しているかのようにこれらのエンドポイントを使用します。

**Response API の使用 (Response API usage)**::
コードでは `use_responses_api=True` を使用して、ChatCompletion ではなく Llama Stack ネイティブの Response API を活用しています。これにより、Llama Stack のツールランタイムとの統合が向上します。

**MCP ツールのバインド (MCP tool binding)**::
ツールは MCP サーバー参照を使用して LLM にバインドされます。LangGraph は Llama Stack に対し、どの MCP サーバーをエージェントで利用可能にするかを伝えます。

Llama Stack の OpenAI 互換エンドポイントは、（ローカルの vLLM を使用する場合）実際の認証を必要としないため、プレースホルダーの API キーを設定できます。

LangGraph の例は、エージェント的な動作を実証しており、グラフベースのオーケストレーションによる明示的な制御フローを備えた、より複雑でステートフルなエージェントシステムの構築に向けた異なるアプローチを提供しています。

直接的なツール呼び出しとの主な違いに注目してください。

**エージェントの推論 (Agent reasoning)**::
エージェントはユーザーのリクエストを分析し、使用するツールを決定し、回答の形式を計画し、自然言語の回答を統合します。

**自然言語インターフェース (Natural language interface)**::
プログラムでツール名やパラメーターを指定するのではなく、「email が thomashardy@example.com の顧客を検索して」といった対話型の入力を提供します。

**ツールの選択 (Tool selection)**::
エージェントは、ユーザーのメッセージから抽出された適切な email パラメーターを使用して `search_customers` を呼び出すことを自律的に決定します。

**回答の統合 (Response synthesis)**::
ツールの結果を受け取った後、エージェントは人間にとって分かりやすい回答を生成し、データを読みやすい形式に整え、さらなるサポートを提案します。

これがエージェント型 AI の力です。LLM がインテリジェントなコーディネーターとして機能し、ユーザーの意図を理解し、適切なツールを選択し、結果を対話形式で提示します。

== まとめ (Summary)

このモジュールでは、MCP ツールと対話するための 2 つのアプローチを探索しました。

**アプローチ 1: Llama Stack クライアント (直接呼び出し) (Approach 1: Llama Stack Client (direct invocation))**::
- コードがワークフローを制御する、プログラムによるツール呼び出し。
- 確定的なワークフロー、テスト、およびルールベースの統合に役立ちます。
- `client.tool_runtime.invoke_tool()` への直接アクセス。
- LLM の推論はなし。純粋なツールの実行です。

**アプローチ 2: Llama Stack を使用した LangGraph (エージェント駆動) (Approach 2: LangGraph with Llama Stack (agent-driven))**::
- ツールの選択について推論する自律型エージェント。
- ユーザー入力のための自然言語インターフェース。
- エージェントがパラメーターを抽出し、ツールを連鎖させ、回答を統合します。

**実証された主要概念**::
* **ツールの検出**: エージェントは、利用可能なツールとその説明を動的に照会できます。
* **MCP の抽象化**: どちらのアプローチでも同じツールが動作します。MCP インターフェースは一貫しています。
* **Llama Stack の柔軟性**: ネイティブクライアント SDK と LangGraph のようなサードパーティフレームワークの両方をサポートしています。
* **Response API の統合**: どちらのアプローチも、効率的な推論のために Llama Stack の Response API を活用しています。

**構築したもの**::
- MCP ツールを検出し検査する Python スクリプト。
- Llama Stack クライアントを使用した直接的なツール呼び出し。
- 顧客および財務に関するクエリを推論する、LangGraph を使用したエージェント。

これで、自然言語の入力からエージェントの推論、ツール呼び出し、MCP サーバー、バックエンド API、およびデータベースに至るまで、完全なエンドツーエンドの接続を実証できました。

次のモジュールでは、Llama Stack ネイティブのエージェント機能について深く掘り下げます。

= Llama Stack による Evals

以下のいずれかの変更は、AI を組み込んだアプリケーションの動作や回答に大きな影響を与える可能性があります。

* モデルベンダー (model vendor)（例：Llama、Qwen、Mistral、Google、OpenAI）
* モデルバージョン (model version)（例：Gemini2.5、Qwen3）
* モデルパラメーター数 (model parameter count)（例：7B、14B、70B）
* モデルの量子化 (model quantization)（例：q4_K_M、fp16）
* モデルサーバーベンダー (model server vendor)（例：vLLM、Ollama、OpenAI）
* モデルサーバーの構成 (model server configuration)（例：tool-call-parser、chat-template）
* プロンプト (prompts)
* そしてもちろん、アプリケーションコード (application code)（例：.py、.js、.ts、.java）

[NOTE]
====
**なぜこれが重要なのですか？** 数学的推論を向上させるモデルのアップグレードが、同時にツール呼び出しの精度を低下させる可能性があります。メモリ使用量を半分にする量子化の変更が、微妙な事実誤認を引き起こすこともあります。自動化された評価（Evals）がなければ、チームは本番環境（これを発見するのに最もコストがかかる場所）でこれらの退行（リグレッション）を発見することになります。
====

Llama Stack には、ファーストクラスの評価 (Evals) 機能が含まれています。Llama Stack の Evals はデータセット駆動型であり、エージェント、ツール、モデルと直接統合されます。これにより、チームは分離されたプロンプトではなく、実際のワークフロー全体で正確性、安全性、および動作を測定できます。ゴールデンアンサー (golden answers)、確定的スコーリング、および LLM-as-judge パターンをサポートすることで、Llama Stack は評価を反復可能、自動化可能、かつ CI/CD フレンドリーにします。これにより、チームは本番環境にデプロイする前に、プロンプト、ツール、モデル、またはエージェントロジックへの変更を自信を持ってテストできます。

したがって、エージェントや LLM をラップするアプリケーションをサポートするために、候補となるモデルの継続的な管理と維持において、自動化された評価実行方法を持つことはミッションクリティカルです。

このモジュールでは、モデル評価（異なる候補モデルに対して実行するテスト）のセットアップと実行方法に焦点を当てます。

[TIP]
====
これらのスコーリング機能は 2 つのカテゴリに分類されます。

* **確定的 (Deterministic) (`basic::*`)** — 高速、バイナリ（0.0 または 1.0）、LLM 呼び出し不要。`subset_of` は、期待される回答が生成された回答のどこかに含まれているかを確認します。`equality` は完全一致を要求します。正解/不正解が明確な事実確認に最適です。
* **LLM-as-Judge (`llm-as-judge::*`)** — 別のモデルを使用して、品質とニュアンスをより詳細なスケールで評価します。コストは高くなりますが、正解が一つではない自由形式の質問を評価できます。
====

**出力内容の理解:**

* `accuracy: 1.0, num_correct: 3.0, num_total: 3` — 3 つのテストケースすべてに合格しました。この集計スコアは、モデルやプロンプトを変更した際のリグレッションを検出するために、長期的に追跡すべきものです。
* 各行の `score: 1.0` は、期待される回答（例：「4」、「blue」、「Shakespeare」）がモデルの生成した回答のどこかに見つかったことを意味します。これが `basic::subset_of` の動作であり、単純な部分文字列チェックです。
* 生成された回答に見られる `<think>` タグは、Qwen3 の思考連鎖（Chain-of-Thought）推論です。モデルは最終的な回答を出す前に「独り言」を言います。スコアラーはこれらのタグを無視し、期待される回答が全文の中に現れるかどうかだけをチェックします。

*basic::subset_of* スコアラーは明確な事実に関する質問には効果的ですが、説明が明快か、正確か、あるいは構成が優れているかを評価することはできません。モデルからの回答文字列をレビューして判断するためのより高度な方法は、LLM-as-judge パターンを使用することです。

=== LLM-as-judge 

このパターンでは、別の LLM（「判定モデル (judge model)」）が候補モデルの回答を 1〜5 のスケールで評価し、書面で根拠を提供します。これにより、バイナリの合格/不合格よりもはるかに豊富なフィードバックが得られます。判定モデルは正確性、明快さ、完全性、および表現を評価できます。トレードオフはコストと速度です。すべての評価において、候補モデルに加えて判定モデルへの推論呼び出しが必要になります。

判定モデルと候補モデルの環境変数を設定します。ここでは、Llama Scout 17B を判定モデルとして使用し、評価対象の候補モデルとして Qwen3 14B を使用します。

[.console-input]
[source,bash,role="copypaste",subs=attributes+]
----
export JUDGE_MODEL=vllm/llama-scout-17b
export CANDIDATE_MODEL=vllm/qwen3-14b
----

LLM-as-judge の例では、以前の *basic-subset-of-evals* というデータセットを再利用しますが、新しいスコーリング機能とベンチマークを動的に登録します。

[.console-output]
[source,bash,subs=attributes+]
----
DATASET_ID = "basic-subset-of-evals"
SCORING_FN_ID = "my-llm-as-judge-scoring-fn"
BENCHMARK_ID = "my-llm-as-judge-benchmark"
----

以下は Python スクリプトからのスニペットです。
```python
# Llama Stack クライアントを作成
client = LlamaStackClient(base_url=LLAMA_STACK_BASE_URL)

try:
    client.scoring_functions.register(
        scoring_fn_id=SCORING_FN_ID,
        description="LLM-as-judge scoring function for evaluating response quality",
        return_type={"type": "string"},
        provider_id="llm-as-judge",
        provider_scoring_fn_id="llm-as-judge-base",
        params={
            "type": "llm_as_judge",
            "judge_model": JUDGE_MODEL,
            "prompt_template": judge_prompt,
        },
    )
    logger.info(f"Scoring function '{SCORING_FN_ID}' registered successfully")
```

== まとめ (Summary)

このモジュールでは以下のことを行いました。

* 質問とゴールデンアンサーの **データセット (dataset)** を Llama Stack に登録しました。
* 確定的 (`basic::subset_of`) および LLM ベース (`llm-as-judge`) の **スコーリング機能 (scoring functions)** を探索しました。
* データセットとスコーリング機能を組み合わせた **ベンチマーク (benchmarks)** を作成しました。
* 候補モデルに対して **評価 (evals)** を実行し、結果をレビューしました。
* 2 つの異なるモデル（Qwen3 と Granite）を比較し、評価がモデルの動作の違いをどのようにキャッチするかを確認しました。

これらの構成要素（データセット、スコーリング機能、ベンチマーク、評価）は、CI/CD パイプラインに統合されるように設計されています。これにより、モデルの変更、プロンプトの更新、または構成のシフトが、本番環境に到達する前に自動的に検証されるようになります。

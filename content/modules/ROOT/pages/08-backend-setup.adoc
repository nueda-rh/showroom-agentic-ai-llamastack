= バックエンドおよび MCP アーキテクチャ (Backend and MCP Architecture)

前のモジュールでは、Llama Stack の API を個別に探索しました。ここでは、Llama Stack エージェントがモデルコンテキストプロトコル (Model Context Protocol: MCP) を介して実際のビジネス機能とどのように対話するかを確認します。このモジュールでは、標準化されたツールインターフェースを通じて、エージェントがエンタープライズ機能（顧客データ、財務取引、注文管理など）にどのようにアクセスできるかを示します。

== API からエージェントツールへ (From APIs to agent tools)

従来のエンタープライズアプリケーションは、REST API を通じてビジネス機能を公開しています。強力ではありますが、これらの API を使用するには、開発者がカスタムの統合コードを記述し、認証を管理し、エラーを処理し、ドメイン固有のスキーマを理解する必要があります。新しいアプリケーションが登場するたびに、統合のための作業が増えることを意味します。

**Llama Stack エージェントはこのパラダイムを変えます。** API 統合をハードコーディングする代わりに、エージェントは以下を行うことができます。

* MCP サーバーを通じて実行時に**ツールを動的に検出**する
* ユーザーの意図に基づいて**どのツールを使用するかを推論**する
* ツール呼び出しを使用して**ビジネス機能を自然に呼び出す**
* さまざまなシステムにわたる**多段階のワークフローを構成**する

エージェントと既存のビジネスシステム間の架け橋となるのが、**モデルコンテキストプロトコル (Model Context Protocol: MCP)** です。

== MCP とは何か、なぜ重要なのか？ (What is MCP and why does it matter?)

モデルコンテキストプロトコル (Model Context Protocol) は、AI エージェントが一貫したインターフェースを通じて外部ツールやデータソースと対話できるようにするためのオープンな標準です。REST API が開発者向けに設計されているのに対し、MCP はエージェント向けに設計された「AI のための API」であると考えてください。

=== MCP はエージェント統合の課題を解決する (MCP solves the agent integration challenge)

**MCP がない場合**、エージェントをビジネスシステムと統合するには以下が必要になります。

* すべての API エンドポイントに対してカスタムツールのラッパーを記述する
* ビジネスロジックをエージェントのプロンプトにハードコーディングする
* 資格情報と認証を個別に管理する
* API が変更されたときにツールを再構築する
* 異なるシステム間で標準化が行われない

**MCP がある場合**、以下のメリットが得られます。

* **標準化されたツールの検出**: エージェントが MCP サーバーに「何ができるか」を問いかけ、構造化されたツールの説明を受け取ります。
* **統合された呼び出しプロトコル**: 基盤となる実装に関係なく、すべてのツールが同じ方法で呼び出されます。
* **セキュリティ境界**: MCP サーバーがアクセスを制御し、リクエストを検証し、ポリシーを適用します。
* **バックエンドの抽象化**: エージェントを壊すことなく、ビジネスシステムを論理的に進化させることができます。
* **エコシステムの互換性**: 任意の MCP 準拠エージェントが、任意の MCP 準拠サーバーを使用できます。

=== Llama Stack がどのように MCP を使用するか (How Llama Stack uses MCP)

Llama Stack は、そのツールランタイムを通じてファーストクラスの MCP サポートを提供します。

1. **MCP サーバーの登録**: MCP エンドポイントをツールグループとして Llama Stack に登録します。
2. **ツールの検出**: Llama Stack が MCP サーバーに対して利用可能なツールを照会します。
3. **エージェントの推論**: エージェントが機能を必要とするとき、Llama Stack はツールを呼び出し可能な状態にします。
4. **ツールの実行**: Llama Stack が MCP ツールを呼び出し、結果をエージェントに返します。
5. **回答の統合**: エージェントはツールの結果を使用して、自然言語の回答を構成します。

このモジュールでは、顧客管理および財務運用のビジネス機能を使用して、このパターンを実証します。

=== エージェントがビジネス機能にアクセスする方法 (How agents access business functions)

**ステップ 1: ユーザーがリクエストを行う**::
ユーザーが自然言語で質問します。「メールアドレスが thomashardy@example.com の顧客を見つけ、その注文履歴を表示して」

**ステップ 2: LLM がリクエストについて推論する**::
エージェントはリクエストを LLM に送信し、LLM はそれを分析して、2 つの機能が必要であると判断します。
- メールアドレスによる顧客の検索
- その顧客の注文履歴の取得

**ステップ 3: ツールの検出**::
Llama Stack は登録された MCP サーバーを照会して、利用可能なツールを見つけます。
- Customer MCP: `search_customers`, `get_customer`
- Finance MCP: `fetch_order_history`, `fetch_invoice_history` など

**ステップ 4: エージェントがツールを呼び出す**::
エージェントは Llama Stack のツールランタイムを介してツールを呼び出します。
1. Customer MCP を介して `search_customers(email="thomashardy@example.com")` を呼び出す
2. 結果から顧客 ID を抽出する
3. Finance MCP を介して `fetch_order_history(customer_id="AROUT")` を呼び出す

**ステップ 5: MCP サーバーがビジネスロジックを実行する**::
各 MCP サーバーは以下を行います。
- リクエストを検証する
- 適切なバックエンド API を呼び出す
- レスポンスを MCP ツール実行結果としてフォーマットする
- データを Llama Stack に返す

**ステップ 6: エージェントが回答を統合する**::
エージェントはツールの結果を受け取り、顧客情報と注文履歴を組み合わせた自然言語の回答を生成します。

== エージェント、MCP、ビジネス機能のフロー (The agent-MCP-business function flow)

MCP は、エージェントの推論とビジネスロジックの実行を明確に分離します。エージェントは REST API、データベーススキーマ、または認証メカニズムについて知る必要はありません。単にツールを呼び出し、構造化された結果を受け取るだけです。

.MCP リクエストフローのシーケンス (MCP request flow sequence)
[mermaid,width=100%]
----
sequenceDiagram
    participant Agent as Llama Stack エージェント
    participant LLS as Llama Stack サーバー
    participant MCP as MCP サーバー

    LLS->>MCP: POST /v1/tool-runtime/invoke<br/>search_customers(email=...)

    API-->>MCP: JSON レスポンス
    MCP->>MCP: MCP 結果としてフォーマット
    MCP-->>LLS: ToolInvocationResult
    LLS->>Agent: 自然言語の回答を統合

    Note over Agent,DB: MCP サーバーはエージェントのツール呼び出しと<br/>バックエンドのビジネス機能を仲介します
----

### エージェントツールとして公開されるビジネス機能 (Business functions exposed as agent tools)

このラボでは、2 つの MCP サーバーがビジネス機能を Llama Stack エージェントに公開します。

**顧客ツール (Customer tools)** (Customer MCP サーバー経由)::
* `search_customers`: 部分一致を含むさまざまな条件で顧客を検索します
* `get_customer`: ID によって完全な顧客詳細を取得します

**財務ツール (Finance tools)** (Finance MCP サーバー経由)::
* `fetch_order_history`: 日付フィルタリングとページネーションを使用して注文履歴を取得します
* `fetch_invoice_history`: 日付フィルタリングとページネーションを使用して請求履歴を取得します

エージェントは、基盤となる API、データベース、または実装の詳細を知ることなく、Llama Stack のツールランタイムを介してこれらのツールを自然に呼び出します。MCP サーバーは、ツール呼び出しをビジネス操作に変換するすべての複雑な処理を担います。

== MCP サーバーのデプロイ (Deploy MCP Servers)

MCP サーバーは、Llama Stack のツール呼び出しプロトコルとバックエンド REST API の間の変換レイヤーとして機能します。各 MCP サーバーは以下を行います。

1. **MCP 仕様の実装**: ツールの検出と呼び出しのための標準化されたエンドポイントを提供します。
2. **バックエンド API のラップ**: MCP ツールの呼び出しを適切な REST API リクエストに変換します。
3. **認証と検証の処理**: 許可された操作のみが実行されるようにします。
4. **レスポンスのフォーマット**: API レスポンスを MCP 互換のツール結果に変換します。

FantaCo のデプロイメントには、ドメインごとに 1 つずつ、計 2 つの MCP サーバーが含まれています。

[NOTE]
====
**MCP サーバーにはビジネスロジックは含まれていません。** これらは、MCP ツールの呼び出しを REST API 呼び出しに変換する薄いアダプターです。実際のビジネスルール、データ検証、およびデータベースクエリはバックエンドサービスに留まります。この分離により、既存のシステムを変更することなく AI 機能を追加できます。
====

== まとめ (Summary)

このモジュールでは、エージェントがビジネス機能にアクセスできるようにするためのインフラストラクチャをデプロイしました。

**バックエンドサービスのデプロイ**::
PostgreSQL データベースを備えた 2 つのマイクロサービス (Customer と Finance) が、現実的なビジネス機能を提供します。

**MCP サーバーのデプロイ**::
2 つの MCP サーバーが Llama Stack とバックエンドサービスの間の架け橋として機能し、エージェントのツール呼び出しを API リクエストに変換します。

**統合の検証**::
curl コマンドを使用して、以下を確認しました。
- バックエンド API が直接の REST 呼び出しに応答すること
- MCP サーバーがデプロイされていること

**実証された主要概念**::
* **エージェントからビジネス機能へのフロー**: エージェントが実装の詳細を知ることなく、エンタープライズ機能にアクセスする方法
* **抽象化レイヤーとしての MCP**: ツールの検出と呼び出しのための標準化されたプロトコル
* **動的なツールの検出**: エージェントはデプロイ時ではなく実行時に利用可能な機能を学習する
* **クリーンな分離**: ビジネスロジックはバックエンドサービスに留まり、MCP は変換を処理し、エージェントは推論を処理する

これで、エージェントがこれらのツールを呼び出すためのインフラストラクチャが整いました。次のモジュールでは、Python クライアント（Llama Stack Client および LangGraph）を使用してこれらの MCP サーバーと対話し、ビジネス機能をインテリジェントに組み合わせて複雑なユーザーの質問に答えます。
